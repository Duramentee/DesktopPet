## 2026-10-20 第一轮：需求梳理、技术选型与第一迭代骨架

### 一、需求确认过程

本轮开始时工作区为空目录，没有既有代码。通过三轮问答确定了需求基线，结论如下。

| 需求项 | 最终结论 | 提出方 | 对设计的影响 |
|---|---|---|---|
| 目标平台 | Windows、Linux、macOS 三个平台都适配，优先级为 Windows 高于 macOS，macOS 高于 Linux | 用户 | 平台层必须以接口抽象，每项系统能力在三个平台上分别实现 |
| 宠物外观 | 需要动画，并且外观必须与逻辑解耦、可以更换 | 用户 | 引入皮肤包概念，逻辑层只引用动画名称 idle 与 drag |
| 养成系统 | 第一迭代不包含养成数值与存档演化 | 用户 | 领域层只包含状态机、动画播放器、位置约束、坐标换算、清单校验、配置处理 |
| 交互深度 | 第一迭代只包含拖拽与右键菜单 | 用户 | 状态机只有待机与拖拽中两个状态 |
| 维护方式 | 由人工智能负责维护，人类不参与日常代码维护 | 用户 | 可读性与人工接手成本不列入目标，改用体积、占用、分发、一致性等可量化目标 |
| 非功能目标 | 打包体积小、运行占用低、分发容易、多平台表现一致、动画流畅、缺陷少 | 用户 | 直接否决了 Electron 方案，改用 Tauri |
| 项目定位 | 自用为主，最多在 GitHub 开源供他人使用，无商业需求 | 用户 | 不申请代码签名证书、不实现自动更新、不实现使用统计、采用 MIT 许可证 |
| 开发环境 | WSL2 加 WSLg，真机验收在 Windows 侧进行 | 用户 | WSL 只承担测试与构建，不承担运行验收 |

### 二、技术选型的两次调整

第一次选型为 Electron 加 TypeScript，理由是三个平台都内嵌 Chromium，渲染结果完全一致。该结论在用户补充「打包体积要小、运行占用要低」之后被推翻：Electron 的安装包在八十到一百二十兆字节量级，待机内存在一百兆字节以上，无法通过工程手段削减。

第二次选型为 Tauri 第二版 加 TypeScript 加 Canvas。判断依据有四条：第一，Windows 安装包可以控制在十五兆字节以内，比 Electron 低一个数量级；第二，WebView2 已随 Windows 十 1803 及以上版本与 Windows 十一预装，分发时不需要引导用户安装运行时；第三，窗口置顶、系统托盘、配置存储三项能力都有官方插件，平台特定代码量小；第四，Canvas 逐帧绘制不经过布局引擎、字体渲染与 CSS 合成，是渲染引擎差异最小的绘制方式。

被否决的另外两个方案是 Wails 第二版 与 Rust 原生自绘。前者在四项指标上与 Tauri 接近但没有明显优势；后者在体积、内存、渲染一致性三项上更强，但需要自行实现三个平台的分层窗口、按像素判定鼠标命中与高清屏缩放，第一迭代出现缺陷的范围明显更大，与「缺陷尽量少」这一目标冲突。

### 三、测试驱动开发的执行过程

第一步先建立工程配置与夹具，然后把需求文档第 9.2 节的十八条用例全部写成测试。第一次运行结果为六个测试文件全部失败，失败原因是被测模块尚不存在，这构成红色阶段。

## 2026-10-20 第二轮：Windows 真机编译、首轮验收与两处缺陷修复

### 一、PowerShell 环境修复

本机 PowerShell 7.6.6 每次启动都会输出一条「术语 oh-my-posh 不会被识别」，同时 `winget` 也无法调用。逐项定位后做了三处修复。

| 问题 | 现象 | 处理方式 |
|---|---|---|
| 启动即报错 | profile 首行调用 `oh-my-posh`，但该程序不在 PATH 上，实际文件在 `%LOCALAPPDATA%\Programs\oh-my-posh\bin` | 把该目录加入用户 PATH；同时改写 profile，命令不存在时回退到上述绝对路径，两者都找不到就静默跳过，不再产生错误 |
| 用户 PATH 重复膨胀 | 用户 PATH 有 52 个条目，其中系统目录与开发工具目录被重复写入三到四次，总长 1658 个字符 | 按首次出现顺序去重后写回，条目降到 26 个、长度降到 927 个字符；去重只删除重复项，不改变任何一条路径的首次出现次序 |
| `winget` 不可用 | `%LOCALAPPDATA%\Microsoft\WindowsApps` 不在 PATH 上，应用执行别名无法解析 | 把该目录加入用户 PATH，`winget --version` 恢复输出 |

修改前的用户 PATH 与旧 profile 已备份到会话目录，需要回滚时可直接取回。

### 二、工具链路线

本机当前账户没有管理员权限，安装 Visual Studio 生成工具会卡在提权，因此没有走构建清单第一段的 MSVC 路线，改用不需要提权的组合。

| 组件 | 获取方式 | 作用 |
|---|---|---|
| Rust 1.99.1，目标 `x86_64-pc-windows-gnu` | `rustup-init.exe -y --default-host x86_64-pc-windows-gnu --default-toolchain stable --profile minimal` | 编译器与标准库 |
| LLVM-MinGW 22.1.8（UCRT 运行时，便携包） | 官方 zip 解压到 `%LOCALAPPDATA%\Programs\llvm-mingw` | `dlltool`、`windres`、`llvm-rc` 等 binutils，供 GNU 目标使用 |

`%USERPROFILE%\.cargo\config.toml` 中固定了三条只对 `x86_64-pc-windows-gnu` 生效的链接参数，原因见下一节。这三条参数属于本机环境配置，不写进仓库，避免影响使用 MSVC 或自带 MinGW 的环境。

### 三、链接阶段接连出现的三个问题

| 问题 | 现象 | 原因与处理 |
|---|---|---|
| 缺少 libgcc | 链接报 `unable to find library -lgcc` 与 `-lgcc_eh` | LLVM-MinGW 用 compiler-rt，不自带 libgcc；加 `-C link-self-contained=yes`，改用 Rust 自带的 mingw 自包含库 |
| 可执行文件启动即崩溃 | tauri 的构建脚本以 `0xC0000005` 退出，cargo 无任何输出；lldb 显示在 `0x14b2a08` 触发 DEP 违规，该地址正是映像内偏移 `0xb2a08` 丢了映像基址，等价于调用了 32 位截断后的函数指针 | LLVM-MinGW 的 gcc 驱动链接出的二进制不可用；改用 `-C linker-flavor=ld.lld -C linker=rust-lld`，直接调用 Rust 工具链自带的 lld |
| debug 构建的 cdylib 导出超限 | `rust-lld: error: too many exported symbols (got 91853, max 65535)` | PE 格式的导出表上限；加 `-C link-arg=--exclude-all-symbols`，只保留 rustc 生成的 `.def` 中列出的导出 |

### 四、真机发现并修复的两处缺陷

这两处问题都无法被单元测试覆盖，只有真正启动窗口才会暴露。

| 缺陷 | 现象 | 根因 | 修复 |
|---|---|---|---|
| 宠物被横向拉伸 | 配置写的是 64×64，`GetWindowRect` 量出来是 136×64，待机图被拉成扁圆 | 窗口仍带 `WS_CAPTION`、`WS_SYSMENU`、`WS_MINIMIZEBOX`、`WS_MAXIMIZEBOX` 样式，Windows 会按最小跟踪宽度（96 DPI 下为 136 像素）撑开窗口 | 新增 `src-tauri/src/window_style.rs`，在 setup 阶段去掉这四个样式并重算窗口框架；非 Windows 平台保留空实现 |
| 窗口尺寸不跟随皮肤 | 画布按皮肤尺寸变化，窗口停留在启动尺寸；修好上一条之后依旧无效 | 能力清单缺少 `core:window:allow-set-size`，前端的尺寸调用被拒绝，只留下一条 warn | 补齐该权限；窗口后端增加 `setSize`，控制器在装载皮肤后把窗口调成皮肤画布尺寸，切换皮肤时用新皮肤的锚点重新对齐窗口左上角 |

第二条还顺带修正了一个原本就存在的问题：切换皮肤时窗口左上角没有按新锚点重算，皮肤锚点若与旧皮肤不同，宠物就会偏移。

## 2026-10-20 第五轮：修复拖动时的位置闪烁

### 一、现象

真机拖动宠物时，窗口在原始位置、目标位置与若干中间位置之间反复闪烁，拖动越快越明显。

### 二、根因

窗口移动事件的处理链路是 `onMoved → syncTopLeft → persistPosition → setTopLeft`，也就是操作系统每移动一次窗口，程序立刻又把窗口设置回“由锚点推算出的位置”，并且顺带写一次磁盘。

系统级拖拽期间，窗口位置由操作系统的模态移动循环负责：它按「按下时的窗口位置 + 指针位移」持续设置窗口位置。程序这边同时在设同一个窗口，两边各自计算、互相覆盖，窗口于是在两个位置之间来回跳；中间位置则来自异步 IPC 的往返延迟。

### 三、修复

| 改动 | 内容 |
|---|---|
| 移动事件只读不写 | `syncTopLeft` 改为 `handleWindowMoved`：只把窗口左上角换算成锚点并重绘，不设置窗口位置、也不写磁盘 |
| 锚点更新不依赖动画状态 | 改用 `place`（不受拖拽状态限制地放置锚点）替代只在拖拽中生效的 `moveTo`，并删除后者，避免位置更新被状态卡住 |
| 兜底结束拖拽 | 系统拖拽期间网页收不到 `pointerup`，因此监听窗口移动并在位置连续静止 400 毫秒后收尾；`pointerUp` 只在处于拖拽时切换动画，之后总是补写一次位置 |
| 顺带修正的旧问题 | 之前每次移动都写一次配置文件，一次拖动会产生上百次磁盘写入；现在只在拖动结束时写一次 |

### 四、验证

| 验证项 | 结果 | 说明 |
|---|---|---|
| 单元测试 | 十四个文件、一百零三个用例通过 | 新增：拖拽期间不设置窗口位置也不写磁盘；拖动结束写回最终锚点；非拖拽状态下结束拖拽只补写位置 |
| 类型检查 | 通过 | |
| 高频拖动采样 | 通过 | 以十五毫秒间隔连续移动五十步，窗口位置严格单调推进（686 至 980），没有出现反向跳变 |
| 最终位置一致性 | 通过 | 拖动结束后配置文件中的锚点与窗口实际位置加锚点偏移完全一致 |
| 拖拽中途停顿 | 通过 | 按住不动一秒以上窗口不跳动，继续移动仍能跟随 |
| 真机确认 | 通过 | 使用者在真实鼠标拖动下确认不再闪烁，拖动正常 |

| 偶尔张望 | 每五到十二秒随机向左或向右偏移最多两个逻辑像素；一百八十毫秒移出、停留一点一秒、一百八十毫秒移回，方向由随机源决定 |
| 开关 | 配置新增 `idleMotion`，缺省为开；右键菜单提供“待机小动作：开/关”，关闭时立即回到中立位姿并停止计时 |
| 与拖拽的关系 | 抓起的瞬间重置位姿，拖拽期间不推进，松开后从呼吸周期的起点重新开始 |

实现上把行为做成纯计算：`IdleMotion` 只接收时间步长，返回 `{ offsetX, offsetY, scaleY }` 位姿；渲染层据此以底边中点做平移与缩放。时间与随机源都可注入，因此行为时序可以精确测试。

## 2026-10-20 第九轮：第七迭代，皮肤包热加载

### 一、本轮解决的问题

随程序分发的皮肤包被嵌在可执行文件里，改一帧或加一套皮肤都必须重新打包。本轮给皮肤加了一个可写目录，并让运行中的程序自己发现变化。

| 功能 | 设计结论 |
|---|---|
| 用户皮肤目录 | `%APPDATA%\<标识>\skins`，按皮肤标识分子目录，结构与应用内皮肤包一致；首次调用时自动创建 |

## 2026-10-20 第十二轮：绘制节流

### 一、本轮解决的问题

日志里的帧率一直是每秒两百帧，而宠物动画本身只有每秒十帧、待机小动作只需要每秒三十帧左右。超出的绘制全部是白做的，还让这个长期驻留的进程一直占着 CPU。

### 二、先把账算清楚

最初的测量只看了主进程，得出「二十秒耗零点三秒 CPU」的结论，其实大头在 WebView2 的子进程里。改成按进程树统计后才看清真实开销（默认配置、待机、二十秒）：

| 进程 | 优化前 CPU 时间 | 优化后 CPU 时间 |
|---|---|---|
| 主进程 | 0.55 秒 | 0.55 秒 |
| WebView2 浏览器进程 | 0.56 秒 | 0.89 秒 |
| 图形进程 | 1.98 秒 | 0.59 秒 |
| 渲染进程 | 1.98 秒 | 1.88 秒 |
| 工具进程等 | 0.14 秒 | 0.33 秒 |
| 合计 | 10.47 秒 | 4.25 秒 |

合计相当于从单核的百分之五十二降到百分之二十一，十六核整机上从百分之三点三降到百分之一点三。多次复测的合计在 3.0 到 4.3 秒之间波动，优化前稳定在 10 秒以上。

### 三、做法

| 环节 | 设计 |
|---|---|
| 节流器 | 新增 `renderer/loop.ts`：按目标帧率判断该不该画，被跳过的时间累加进下一次推进，动画时间轴不会走偏 |
| 重复绘制跳过 | 控制器记录内容指纹（帧文件、画布尺寸、位姿），完全相同时不重画；关闭待机小动作时每秒只画真正的换帧 |
| 强制重画 | 换皮肤与缩放变化会重建图片与画布后备存储，此时清空指纹强制画一次，避免留下空白 |
| 统计口径 | 帧率统计改为真实绘制间隔，托盘提示与日志里的数字从此是实际绘制帧率 |
| 绘制上限 | 每秒三十帧，兼顾呼吸平移的平滑度与功耗 |

试过但也放弃的方案：用定时器替代动画回调。定时器能进一步压低唤醒次数（渲染进程从 2.59 秒降到 1.38 秒），但 Windows 的定时器会被合并到约十五毫秒精度，实测只能跑到每秒二十二到二十三帧，触发帧率告警且能看出顿感，因此保留动画回调做时钟、只在回调里做节流。

## 2026-10-22 第十四轮：从视频制作皮肤与中文标识支持

### 一、本轮目标

用户提供了一段白底待机动画视频（`waiting.mp4`，1440×1440、24 帧每秒、121 帧）与十五张大尺寸素材图，要做成能用的皮肤。按需求文档的流程，这一步既要产出皮肤，也要把“以后再做下一份皮肤”的动作固定成脚本。

### 二、踩到的坑与修法

| 现象 | 根因 | 修法 |
|---|---|---|
| 皮肤目录、清单、帧都齐全，程序却回退到占位皮肤，日志里只有一行“启动完成：画布 64x64” | 自定义协议拿到的请求路径是百分号编码的（`%E4%BA%9A%E8%B4%9E`），后端直接拿去拼文件路径，中文目录必然读不到 | 新增 `percent_decode`，解码后再做逐段校验；顺带补了五条 Rust 用例，其中一条覆盖 `%2F` 解码后被路径校验拒绝的情况 |
| 皮肤坏掉时完全无感，只能靠肉眼看出“换了个样子” | 回退逻辑是静默的 | 控制器新增 `onSkinFailure` 回调，回退时把编号与原因写进日志；补了两条用例 |
| 26 兆字节的原始素材被提交进 `assets/`，而 `assets` 是 Vite 的 `publicDir`，会整套打进安装包 | 素材直接放在皮肤目录里 | 素材移到仓库根的 `sources/<皮肤标识>/`；`assets` 只留清单与帧图片；新增用例拦截混进 `assets` 的视频与超过五百一十二千字节的图片 |

### 三、制作流程

新增 `scripts/build-skin-from-video.py`，一次跑完六步：

| 步骤 | 做法 |
|---|---|
| 抽帧 | `ffmpeg -vf fps=12`，二十四帧每秒的源取出每秒十二帧 |
| 抠白底 | 取近白像素（三通道都不低于 238）做连通域，只有与画面边缘连通的白色才算背景；被深色描边包围的白色衣料、高光因此不会丢 |
| 去水印 | 只保留最大的一块前景连通域，角落里与主体不相连的水印随之消失 |
| 统一缩放 | 用全部帧的并集包围盒算一个缩放比例，底部对齐、水平居中放进画布，避免逐帧取包围盒导致的抖动 |
| 压体积 | 每帧转成 255 色调色板 PNG：真彩色合计 870 KB，调色板后 250 KB，四倍放大下看不出差别 |
| 出清单 | 写 `skin.json` 并把皮肤登记进 `assets/skins/index.json` |

拖拽动画在连续帧里挑一段步长均匀、又不至于静止的窗口，再按“正放再倒放”排列，因此循环的首尾都只差一步；早期版本直接取首尾两帧，两帧相差极大，交替播放时看起来像在抽搐。

### 四、验证结果

| 验证项 | 结果 | 说明 |
|---|---|---|
| 自动化测试 | 二十二个文件、一百六十二个用例通过 | 新增 Rust 五条、控制器两条、皮肤资产两条 |
| 中文标识加载 | 通过 | 修复前回退到 64×64 占位皮肤，修复后日志显示 `画布 96x96`，配置里的 `activeSkinId` 保持 `亚贞` |
| 内置皮肤加载 | 通过 | 删掉用户目录里的副本后重启，仍以 96×96 加载，证明打包路径同样可用 |
| 外观 | 通过 | 截图放大四倍核对：无白底、无边框、无水印、深色与浅色背景上都没有白边 |
| 点击穿透 | 通过 | 直接读窗口扩展样式：透明处 `WS_EX_TRANSPARENT` 置位，宠物身体处清除，来回切换稳定无抖动 |

## 2026-10-22 第十五轮：修复拖动时动画抽动

### 一、现象

拖动宠物时画面在抽动，看起来像两幅画面在快速交替。

### 二、根因

拖拽动画只有两帧，且这两帧取自视频的第零帧与第三十帧（五秒视频的中点）。测得两帧平均差 23.98，而相邻帧只有 1.65，相差十四倍；十二帧每秒交替播放，就是每秒六次在两个差别极大的姿态之间反复跳。

这是第十一轮生成脚本的设计问题：当时想用“首尾两段画面”表现被拎起来的晃动，忽略了首尾两帧在时间上隔了两秒半。

### 三、修法

拖拽动画改为从连续帧里挑一段窗口，按“正放再倒放”排列：

| 环节 | 做法 |
|---|---|
| 选窗口 | 对每个候选窗口算相邻帧差之和与最大单步差；先剔除动量不足最剧烈窗口三成的（避免看起来冻结），再取最大单步差最小的 |
| 排列 | 五帧正放加中间三帧倒放，共八帧；循环首尾只差一步，接缝差 2.13，与普通相邻帧同量级 |
| 帧率 | 仍是十二帧每秒，一个来回约零点六七秒 |

改动在 `scripts/build-skin-from-video.py` 的 `pick_drag_sequence` 中，重新生成后待机帧逐字节不变（`idle_0.png` 哈希一致），只有拖拽帧变化。

### 四、验证

| 验证项 | 结果 | 说明 |
|---|---|---|
| 帧序列 | 通过 | 用 WebView2 远程调试钩住 `drawImage`，记录实际绘制的帧名：按住不放的两秒内依次是 `drag_0` 到 `drag_7` 再回到 `drag_0`，每 0.4 秒推进五帧，没有回头跳 |
| 释放后 | 通过 | 松手后切换为 `idle_0` 起的顺序推进 |
| 渲染未被拖动阻塞 | 通过 | 同一时间采样页面里的 `requestAnimationFrame` 计数，全程约每秒 210 次，说明系统拖拽的模态循环没有卡住渲染 |
| 帧间差 | 通过 | 拖拽八帧相邻差 2.13 到 3.31，接缝 2.13；改动前是 23.98 |
| 位移 | 通过 | 二十步拖动窗口横坐标严格单调，零反向跳变 |
| 自动化测试 | 通过 | 二十二个文件、一百六十二个用例 |

排查中确认过一条：像素截图不能用来判断拖动中的动画，因为窗口在移动、透明处显示的是桌面，截图差会被背景污染；必须回到帧名与渲染计数上才能得到干净结论。

## 2026-10-22 第十六轮：持续集成

### 一、本轮做的事

仓库此前没有任何自动化关卡：一百六十二个前端用例、类型检查、Rust 单元测试全靠本地手工执行，而且只有 Windows 一台机器，Linux 侧的 Rust 代码从未编译过。

新增 `.github/workflows/ci.yml`，每次推送到 `main` 与每个拉取请求都跑三个任务：

| 任务 | 运行环境 | 内容 |
|---|---|---|
| 前端 | `ubuntu-24.04` | `npm ci`、`npm run typecheck`、`npm test`、`npm run build`，并打印 `dist` 与 `dist/skins` 体积 |
| Rust · Linux | `ubuntu-24.04` | 先装 WebKitGTK、GTK、libayatana-appindicator、librsvg、libxdo、patchelf，再跑格式检查、静态检查、单元测试 |
| Rust · Windows | `windows-latest` | 同样的三条 Rust 检查，使用运行器自带的 MSVC 工具链 |

顺带做的两件小事：用 `cargo fmt` 把 Rust 代码统一格式化（五个文件、十八行增删，纯排版），确认 `cargo clippy --all-targets` 零告警后把 `-D warnings` 写进 CI，让告警直接变成失败。

### 二、验证结果

首次运行三个任务全部通过，用时约六分钟：

| 任务 | 结果 | 附带结论 |
|---|---|---|

| Rust · Linux | 通过 | 这是本仓库第一次真正在 Linux 上编译 Tauri 应用并跑通测试，补齐了“从未在 Linux 编译”的空缺 |
| Rust · Windows | 通过 | `src-tauri/.cargo/config.toml` 里那三条只对 GNU 目标生效的链接参数没有影响 MSVC 构建 |

### 三、仍然缺的部分

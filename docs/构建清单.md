# 三段构建清单

> 本清单面向 Windows 原生环境。WSL 只承担自动化测试职责，不承担运行与验收职责，原因见 `docs/需求说明.md` 第 2.1 节。
> 三段之间的顺序不可交换：第二段依赖第一段的工具链，第三段依赖第二段安装完成的依赖。

## 第一段：准备工具链

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1.1 | 以管理员身份打开 PowerShell | 安装 Visual Studio 生成工具需要管理员权限 |
| 1.2 | 执行下表三条安装命令 | 分别安装 Node.js 长期支持版、Rust 工具链与 C++ 生成工具 |
| 1.3 | 关闭并重新打开 PowerShell | 安装程序会修改 PATH 变量，只有新开的终端才能读到 |
| 1.4 | 执行验证命令并核对版本输出 | 四项都有版本号输出才表示第一段完成 |

```powershell
winget install --id OpenJS.NodeJS.LTS -e
winget install --id Rustlang.Rustup -e
winget install --id Microsoft.VisualStudio.2022.BuildTools -e --override "--wait --passive --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"
```

第一条命令安装 Node.js 与 npm；第二条命令安装 Rust 工具链，rustup 在 Windows 上默认使用 MSVC 目标；第三条命令安装 Visual Studio 生成工具，只安装「使用 C++ 的桌面开发」这一项负载，因为 Rust 在 Windows 上需要一个 C++ 链接器。

```powershell
node -v
npm -v
rustc -V
cargo -V
```

四项验证的预期结果是：Node.js 输出二十或更高的版本号，npm 输出十或更高的版本号，rustc 与 cargo 输出一点七七或更高的版本号。若 `rustc -V` 报找不到命令，说明安装后没有重开终端，或者 PATH 中缺少 `%USERPROFILE%\.cargo\bin`。

WebView2 运行时在 Windows 十一与较新的 Windows 十上已经预装，无需单独安装。若在执行第三段时出现找不到 WebView2 的错误，从微软官网下载「WebView2 常青版独立安装程序」安装一次即可。

### 第一段的替代路线：没有管理员权限时

VS 生成工具必须提权安装。如果当前账户拿不到管理员权限，可以改用 GNU 目标加 LLVM-MinGW，整条路线都不需要提权。这条路线在 Windows 侧实测可以完成编译、启动与验收，产出的程序与 MSVC 路线行为一致。

```powershell
# 1. 安装 Rust，宿主目标指定为 GNU
curl.exe -L -o "$env:TEMP\rustup-init.exe" `
  https://static.rust-lang.org/rustup/dist/x86_64-pc-windows-gnu/rustup-init.exe
& "$env:TEMP\rustup-init.exe" -y --default-host x86_64-pc-windows-gnu --default-toolchain stable --profile minimal

# 2. 下载 LLVM-MinGW 便携包并解压，提供 dlltool、windres 等 binutils
curl.exe -L -o "$env:TEMP\llvm-mingw.zip" `
  https://github.com/mstorsjo/llvm-mingw/releases/download/20260616/llvm-mingw-20260616-ucrt-x86_64.zip
Expand-Archive "$env:TEMP\llvm-mingw.zip" -DestinationPath "$env:LOCALAPPDATA\Programs\llvm-mingw" -Force

# 3. 把 Cargo 的 bin 目录与 LLVM-MinGW 的 bin 目录加入用户 PATH，然后重开终端
```

链接参数已经随仓库提供，位于 `src-tauri/.cargo/config.toml`，只对 `x86_64-pc-windows-gnu` 目标生效，使用 MSVC 工具链时不会生效，无需手工改动。三条参数缺一不可：第一条补上 LLVM-MinGW 缺失的 libgcc，第二条绕开其 gcc 驱动链接出的损坏二进制，第三条避免 debug 构建的 cdylib 导出符号超过 PE 上限。

```toml
[target.x86_64-pc-windows-gnu]
rustflags = [
  "-C", "link-self-contained=yes",
  "-C", "linker-flavor=ld.lld",
  "-C", "linker=rust-lld",
  "-C", "link-arg=--exclude-all-symbols",
]
```

之后第二段与第三段的命令完全相同，验证标准是 `rustc -V` 输出 `1.99` 以上、`cargo -V` 有输出、`cargo check` 在 `src-tauri` 目录下无错误。

## 第二段：获取代码并安装依赖

| 步骤 | 操作 | 说明 |
|---|---|---|
| 2.1 | 在 Windows 文件系统中选定目录 | 建议使用 `C:\dev`，不要使用网络共享或者 WSL 的 UNC 路径，否则编译速度会明显下降 |
| 2.2 | 克隆仓库 | 使用 HTTPS 地址，需要凭据时由 Git 凭据管理器负责保存 |
| 2.3 | 安装前端依赖 | 依赖中包含与平台绑定的原生二进制，因此必须在 Windows 侧重新安装，不能复用 WSL 侧的 `node_modules` |
| 2.4 | 执行测试与类型检查 | 用例全部通过才进入第三段 |

```powershell
mkdir C:\dev -Force
cd C:\dev
git clone https://github.com/Duramentee/DesktopPet.git DesktopPet
cd DesktopPet
npm install
npm test
npm run typecheck
```

验证标准是 `npm test` 输出十四个测试文件、一百零一个用例全部通过，`npm run typecheck` 无任何输出。若测试数量与上述不符，说明代码版本与工作日志记录的不一致，需要先核对提交记录。

## 第三段：启动、验收与打包

| 步骤 | 操作 | 说明 |
|---|---|---|
| 3.1 | 启动开发模式 | 首次启动会编译 Rust 依赖，耗时明显长于后续启动，属于正常现象 |
| 3.2 | 逐项执行手工验收 | 验收清单见 `docs/需求说明.md` 第 9.3 节，共七项 |
| 3.3 | 测量体积与内存 | 用于核对需求文档第 3.1 节的两项硬性目标 |
| 3.4 | 构建发布产物 | 产出安装程序，用于分发 |

```powershell
npm run tauri dev
```

启动成功的判断标准是宠物出现在桌面右下角附近，待机动画持续循环。首次启动若停留在「编译中」较长时间，属于 Rust 依赖的首次编译，后续启动不再重复。

七项手工验收的内容是：透明背景、窗口置顶、拖拽平滑度、右键菜单、系统托盘、位置记忆、皮肤切换。每一项的通过标准见需求文档第 9.3 节，验收过程中出现失败项时记录现象、平台版本与会话类型，再回到代码定位。

```powershell
npm run tauri build
Get-ChildItem src-tauri\target\release\bundle -Recurse -Include *.msi,*.exe |
  Select-Object Name, @{Name='兆字节';Expression={[math]::Round($_.Length/1MB,2)}}
```

体积验收标准是安装程序不超过十五兆字节。若明显超出，先检查是否在 `src-tauri/Cargo.toml` 的发布配置中保留了 `lto`、`opt-level = "s"` 与 `strip` 三项设置。

```powershell
Start-Process src-tauri\target\release\desktop-pet.exe
Get-Process desktop-pet | Select-Object Name, @{Name='内存兆字节';Expression={[math]::Round($_.WorkingSet64/1MB,2)}}
```

内存验收标准是待机状态常驻内存不超过八十兆字节。测量时需要在宠物安静播放待机动画十秒之后取数，不能取刚启动时仍在加载资源的那一瞬间。

## 备用路径：在 WSL 中只跑自动化测试

WSL 侧的用途只有一项：在没有图形界面的情况下快速验证逻辑改动。

```bash
cd /home/drow/DesktopPet
npm test
npm run typecheck
npm run build
npm run skin:generate
```

四条命令分别对应单元测试、类型检查、前端构建与资源生成，都不需要图形会话，因此可以在 WSL 中完整执行。不要在这四条命令之外期待任何与窗口表现有关的结论。

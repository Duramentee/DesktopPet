# 桌面宠物需求说明

> 文档状态：第一版，由需求讨论产生，尚未冻结。
> 编写日期：2026-10-20。
> 适用范围：本文件描述第一个迭代的全部需求、限制与验收标准，后续功能变更需要先修改本文件。

## 1. 项目定位

本项目交付一个运行在桌面最上层的宠物窗口。宠物自身提供一段循环播放的待机动画，用户可以按住宠物把它拖动到屏幕上的任意位置，并且可以通过右键菜单执行退出与置顶开关两项命令。宠物的外观完全由外部皮肤包决定，程序本身不包含任何硬编码的形象资源。

## 2. 平台支持矩阵与能力声明

三个操作系统都属于第一支持目标，但受到操作系统协议限制的部分能力必须如实声明，不能承诺在全部环境下行为一致。

| 系统能力 | Windows | macOS | Linux 的 X11 会话 | Linux 的 Wayland 会话 |
|---|---|---|---|---|
| 透明无边框窗口 | 完整支持 | 完整支持 | 完整支持，前提是窗口合成器正在运行 | 支持，但需要较新版本的 Electron 与合成器配合，否则可能出现灰底 |
| 窗口置顶 | 完整支持 | 完整支持 | 完整支持 | 尽力支持，因为 Wayland 协议不允许应用自行决定窗口层级，实际结果取决于合成器是否采纳应用提出的请求 |
| 鼠标穿透 | 完整支持，并且可以限定为仅在宠物图像范围内响应点击 | 完整支持，并且可以限定为仅在宠物图像范围内响应点击 | 完整支持，前提是合成器支持输入区域设置 | 尽力支持，因为多数合成器不采纳应用提出的输入区域设置，此时透明区域会拦截桌面图标的点击 |
| 系统托盘 | 完整支持 | 完整支持 | 支持，但要求桌面环境提供 StatusNotifier 或 AppIndicator 扩展，未提供的环境下不显示托盘图标 | 与左侧相同 |
| 开机自启 | 通过注册表启动项实现 | 通过 LaunchAgent 实现 | 通过 `~/.config/autostart` 目录中的桌面条目实现 | 与左侧相同 |

第一迭代不实现开机自启，本行内容只作为后续迭代的约束记录。

上表列出的能力差异来自操作系统自身的协议与合成器规则，不来自所选应用框架，因此更换框架不会改变这张矩阵的任何一格。表中「尽力支持」的含义是：程序会发出对应的请求，但无法保证操作系统采纳该请求，因此同一项功能在不同设备上可能表现为可用或不可用，程序必须在这种失效情况下仍然保持可用，不能因为请求未被采纳而抛出异常或者停止响应。

### 2.1 WSL 环境的定位与限制

作者当前的开发机运行 WSL2，图形输出由 WSLg 提供。WSLg 在虚拟机内部运行一个合成器，再通过远程桌面协议把 Linux 窗口转发到 Windows 桌面，因此它不具备原生 Linux 桌面所具备的窗口层级控制与托盘协议转发能力。

| 能力 | WSLg 环境下的实际表现 | 机制原因 |
|---|---|---|
| 透明窗口 | 宠物周围的区域可能显示为不透明底色 | WSLg 经远程桌面协议合成窗口，透明通道的传递依赖于具体的远程桌面配置，不能保证保留 |
| 窗口置顶 | 请求被忽略，宠物无法保持在其他窗口之上 | WSLg 使用的合成器不采纳窗口层级请求，该请求由协议规定而非由应用决定 |
| 鼠标穿透 | 请求被忽略，宠物画布范围之外的区域仍然拦截鼠标事件 | 输入区域请求同样由合成器决定是否采纳 |
| 系统托盘 | 托盘图标不出现 | WSLg 不把 Linux 的 StatusNotifier 协议转发到 Windows 的通知区域 |
| 动画流畅度 | 帧间隔抖动明显大于原生桌面 | 渲染结果需要经远程桌面协议传输，帧间延迟不稳定 |

因此本项目把 WSL 明确区分为两种用途：作为开发与自动化测试环境，WSL 具备完整能力，单元测试、类型检查、前端构建与资源生成全部在其中完成；作为运行与验收环境，WSL 不具备能力，全部手工验收项必须在原生 Windows 上执行。Linux 平台的验收不在 WSL 中进行，而是留待真实 Linux 桌面或 X11 虚拟机。

程序在启动时会调用 Rust 侧的 runtime_info 命令读取操作系统类别、WSL 发行版名称与 WSLg 挂载点三项事实，然后按上述限制表输出警告日志，使降级表现有明确原因可循，而不是表现为无原因的异常。

## 3. 非功能目标与技术选型

### 3.1 非功能目标

项目由人工智能协助维护，人类维护者不参与日常代码维护，因此可读性与人工接手成本不列入目标。项目以作者自用为主，不追求商业目标，同时在 GitHub 上以开源项目的形式发布供他人使用。在上述前提下，项目采用下面九项可以用数字衡量或者可以用固定步骤验收的目标。

| 目标 | 量化标准 | 测量方式 | 未达成该目标造成的后果 |
|---|---|---|---|
| 安装包体积 | Windows 安装程序不超过十五兆字节；macOS 磁盘映像不超过二十兆字节；Linux AppImage 不超过八十兆字节 | 每次打包后把产物大小写入发布记录并与上一版比较 | 用户下载与安装的时间变长，可接受度下降 |
| 运行内存占用 | 待机状态下常驻内存不超过八十兆字节；拖拽过程中不超过一百二十兆字节 | 在三个平台上分别用任务管理器、活动监视器、`smem` 记录空闲与拖拽两种状态的数值 | 桌面宠物属于长期驻留进程，占用过高会引起用户反感 |
| 启动时间 | 从执行程序到宠物第一次出现在屏幕上不超过一点五秒 | 在三个平台上各测量十次并取中位数 | 启动迟滞会让程序显得不可靠 |
| 分发容易 | 将三个平台的产物作为附件上传到 GitHub Releases 供直接下载；Windows 提供单个安装程序，macOS 提供单个磁盘映像，Linux 提供单个 AppImage 与一个 deb 软件包；仓库根目录提供一份从头编译的说明文档 | 在一台干净的虚拟机中，先按下载路径走一遍安装与运行，再按编译说明走一遍从源码到运行的完整流程 | 使用者在安装环节或者编译环节放弃使用 |
| 多平台表现一致 | 同一份皮肤包在三个平台上得到的画布尺寸、锚点换算结果、动画帧序完全一致；允许存在的差异仅限亚像素抗锯齿与透明通道合成方式 | 用同一份录屏素材在三个平台上逐帧比对 | 皮肤作者需要为不同平台准备多套资源，违背皮肤可更换的设计目标 |
| 动画流畅 | 待机动画在三个平台上都以显示器刷新率稳定播放，不出现可被观察者察觉的掉帧 | 在三个平台上录制屏幕并以逐帧时间戳统计帧间隔的方差 | 动画卡顿会直接破坏桌面宠物的体验 |
| 缺陷数量 | 第一迭代结束时，领域层与资源层的自动化测试全部通过，手工验收清单全部通过 | 以测试报告与验收记录为准 | 桌面宠物长期驻留运行，任何未捕获异常都会导致进程退出，用户感知为宠物突然消失 |
| 无网络请求 | 程序在待机、拖拽、切换皮肤、退出四种状态下都不发起任何网络连接，也不读取用户数据目录之外的任何文件 | 在三个平台上分别用系统自带的连接监控工具记录程序的连接记录，期望结果为空；并在代码层面确认不存在网络相关依赖 | 引入网络请求意味着需要处理连接失败、证书与隐私披露，与本项目的自用定位不相容 |
| 平台优先级 | Windows 为第一优先平台，macOS 为第二优先平台，Linux 为第三优先平台 | 当某一项能力在三个平台上的实现成本差异过大时，按此顺序决定实现质量的下限 | 在三个平台上平均用力会导致每个平台都达不到可用标准 |

平台优先级的具体执行方式是：Windows 上全部功能必须完整可用并且通过手工验收；macOS 上允许存在已知的视觉差异，但功能必须完整可用；Linux 上允许置顶与穿透在 Wayland 会话中失效，但 X11 会话中功能必须完整可用。

关于分发容易这一项，有两个平台会给出安全提示，处理方式是在仓库文档中写明放行步骤，不在代码层面做规避。macOS 自 Catalina 起对未签名应用执行强制校验，未经过苹果公证的程序在用户首次打开时会被系统阻止，用户必须手动前往系统设置的隐私与安全性页面选择放行；Windows 的 Microsoft Defender SmartScreen 会对下载次数较少的未知发布者程序显示蓝色提示框，用户必须点击「仍要运行」。消除这两类提示需要按年付费的开发者证书，在自用与无商业收益的前提下，年费成本与收益不成比例，因此明确接受这两类提示并写入使用文档。

### 3.2 候选方案对比

下表按新的非功能目标重新评估四个候选方案，评估所用的体积与内存数值取自各方案官方文档与公开的实测数据，属于数量级参考值，最终数值以本项目的实际打包与测量结果为准。

| 对比维度 | Electron 加 TypeScript | Tauri 第二版 加 TypeScript | Wails 第二版 加 Go | Rust 原生自绘 加 winit |
|---|---|---|---|---|
| Windows 安装包体积 | 八十到一百二十兆字节，因为安装包内需要携带完整的 Chromium 与 Node.js 运行时 | 五到十兆字节，因为渲染依赖系统预装的 WebView2 运行时 | 五到十兆字节，因为渲染依赖系统预装的 WebView2 运行时 | 三到八兆字节，因为只需要携带程序本身与图像解码库 |
| macOS 磁盘映像体积 | 八十到一百二十兆字节 | 八到十二兆字节，因为渲染依赖系统自带的 WebKit | 八到十二兆字节 | 三到八兆字节 |
| Linux 分发体积 | 八十到一百二十兆字节 | 若依赖系统 WebKitGTK 则约十兆字节，若把 WebKitGTK 一起打包则约八十兆字节 | 与左侧同列的情况相同 | 三到八兆字节，只依赖 X11 或 Wayland 客户端库 |
| 待机常驻内存 | 一百到一百五十兆字节 | 四十到七十兆字节，其中 WebView2 在 Windows 上由多个应用共享同一个浏览器进程，因此第二款应用带来的增量明显低于 Electron | 四十到七十兆字节 | 二十到四十兆字节 |
| 透明窗口 | 支持 | 支持；macOS 需要启用私有 API 开关，Linux 的 WebKitGTK 在部分合成器下会出现不透明底色 | 支持，限制与左侧同列的情况相同 | 需要自行调用平台接口：Windows 采用分层窗口，macOS 采用无边框透明视图，Linux 采用 X11 形状扩展 |
| 按图像范围判定鼠标命中 | 支持，在渲染层做像素级判定后调用忽略鼠标事件接口 | 支持，做法与左侧同列相同 | 支持，做法与左侧同列相同 | 需要自行实现命中判定并把结果写回窗口区域 |
| 三平台渲染一致性 | 完全一致，因为三个平台都使用同一个 Chromium 版本 | 渲染引擎不同，逐帧图片的绘制结果基本一致，差异集中在亚像素抗锯齿与透明通道合成 | 与左侧同列的情况相同 | 完全一致，因为像素由程序自己合成 |
| 动画时序一致性 | 一致，请求动画帧回调在三个平台上都对齐显示器垂直同步 | 一致，请求动画帧回调在三个平台上都对齐显示器垂直同步 | 一致 | 需要自行实现垂直同步等待，正确实现后一致 |
| 平台特定代码量 | 少，四项系统能力都有现成接口 | 少，窗口、托盘、自动启动、配置存储四项能力都有官方插件 | 少 | 多，每条系统能力都需要为三个平台各写一份实现 |
| 第一迭代出现缺陷的风险 | 低，因为平台差异已经被框架吸收 | 中，风险集中在透明窗口与鼠标穿透两项能力上 | 中，与左侧同列的情况相同 | 中高，风险集中在透明窗口、命中判定、高清屏缩放三项能力上 |

### 3.3 最终选型

最终选型为 Tauri 第二版 加 TypeScript 加 Canvas，单元测试使用 Vitest，Rust 侧使用 cargo test。

选择该方案的理由按优先级排列如下。第一条理由是它同时满足体积与占用两项硬性目标：Windows 安装包可以控制在十五兆字节以内，而 Electron 在一百兆字节量级，两者相差一个数量级。第二条理由是 Windows 属于第一优先平台，而 WebView2 运行时已经随 Windows 十的 1803 及以上版本与 Windows 十一预装，因此分发时不需要额外引导用户安装运行时，这一点直接满足分发容易这一目标。第三条理由是 Tauri 第二版为窗口置顶、系统托盘、配置存储三项能力提供了官方插件，平台特定代码量因此维持在很小的规模，这一点满足缺陷数量尽量少这一目标。第四条理由是 Canvas 逐帧绘制是三平台渲染引擎差异最小的绘制方式，因为它不依赖布局引擎、字体渲染与 CSS 合成，只做位图缩放与叠加。

该方案需要如实接受的代价有三条。第一条代价是三个平台的渲染引擎不同，亚像素抗锯齿与透明通道合成结果可能存在细微差异，项目通过「同一份录屏逐帧比对」的手工验收来确认差异是否落在允许范围内。第二条代价是 Linux 端依赖系统的 WebKitGTK 库，缺少该库的发行版需要用户自行安装，由于 Linux 属于第三优先平台，该代价被接受。第三条代价是 macOS 的透明窗口需要启用私有 API 开关，该开关只在提交到苹果应用商店时构成限制，桌面直接分发不受影响。

### 3.4 决策修正记录

| 条目 | 上一版结论 | 本版结论 | 修正原因 |
|---|---|---|---|
| 应用框架 | Electron | Tauri 第二版 | 新增打包体积不超过十五兆字节与待机内存不超过八十兆字节两项硬性目标，Electron 无法满足 |
| 渲染方式 | Canvas 绘制 | 保持 Canvas 绘制，运行在 WebView 内部 | Canvas 逐帧绘制对渲染引擎差异最不敏感，因此在渲染引擎不一致的前提下风险最低 |
| 领域层语言 | TypeScript | 保持 TypeScript，运行在 WebView 内部 | 状态机与动画推进紧邻输入事件与渲染循环，放在 WebView 内部可以使每一帧的推进不经过进程间通信 |
| 平台层语言 | TypeScript，运行在 Electron 主进程 | Rust，通过 Tauri 命令暴露给前端 | Rust 侧只承担窗口控制、系统托盘、配置文件读写三类职责，逻辑规模很小，并且可以直接用 cargo test 覆盖纯计算部分 |
| 打包方式 | electron-builder | Tauri 自带打包器 | 与框架选型保持一致，Windows 产出安装程序、macOS 产出磁盘映像、Linux 产出 AppImage 与 deb |
| 前端框架 | 不引入 | 保持不引入 | 界面只有宠物画布与右键菜单两部分，引入前端框架对体积与占用都是净增项 |
| 美术资源 | 程序生成的占位图形 | 保持程序生成的占位图形 | 占位图形由脚本生成，可以被版本控制系统以文本形式保存，并且不增加分发体积 |

### 3.5 使用范围与分发策略

项目定位为作者自用，最多在 GitHub 上以开源项目的形式发布供他人自行使用。该定位决定了项目不需要建设的部分与可以接受的不便，下表把每一项都写明，避免实现阶段把商业产品的习惯性需求带入本项目。

| 条目 | 结论 | 对项目产生的影响 |
|---|---|---|
| 使用范围 | 作者日常自用为主要场景，GitHub 开源发布为次要场景 | 不需要考虑商业授权、服务端部署、用户账号体系与多租户隔离 |
| 分发渠道 | 以 GitHub Releases 的预编译产物为主，以仓库中的编译说明为补充 | 不需要自建下载服务器，不需要维护版本清单服务 |
| 自动更新 | 第一迭代不实现 | 自动更新需要在客户端内置签名公钥、在服务器端维护版本清单，并且会引入一条网络请求，与上表的无网络请求目标直接冲突 |
| 使用统计与崩溃上报 | 不实现 | 程序不采集任何使用数据，进程异常退出时只把错误写入本地日志文件 |
| 代码签名与公证 | 不执行 | macOS 与 Windows 都会给出安全提示，仓库文档中给出放行步骤，用户需要手动操作一次 |
| 多语言界面 | 第一迭代只提供中文界面 | 界面文本集中放在一个文件里，后续需要其他语言时只添加语言包，不修改业务代码 |
| 许可证 | 采用 MIT 许可证 | 允许他人自由使用、修改与再分发，同时保留作者免责条款；第三方皮肤资源若由他人提供，其许可证由提供者自行声明，项目本身只附带自生成的占位皮肤 |
| 兼容范围 | 只对作者实际使用的设备与操作系统版本做验收 | 第三方环境的失败报告可能不处理，README 中写明最小系统版本要求 |
| 贡献方式 | 接受缺陷报告与皮肤包贡献，第一迭代不建立贡献流程文档 | 第一迭代的代码改动全部由作者与合作的人工智能完成 |

## 4. 分层架构与依赖方向

代码分为五层，依赖方向严格单向，只允许上层依赖下层，禁止反向依赖。

| 层次 | 目录 | 职责 | 允许依赖的内容 | 是否可以被无头自动化测试覆盖 |
|---|---|---|---|---|
| 领域层 | `src/core/` | 维护状态机、推进动画帧、计算位置约束、换算锚点坐标、校验皮肤清单与配置文件 | 只允许依赖标准库与自身 | 可以完全覆盖，测试中不创建窗口、不读取系统时钟、不访问真实文件系统 |
| 应用层 | `src/app/` | 把外部事件转换成领域层命令，把领域层产生的状态变化转换成渲染指令与持久化请求 | 领域层与适配层接口定义 | 可以覆盖，测试中使用桩对象替换渲染器与存储组件 |
| 渲染层 | `src/renderer/` | 接收应用层给出的帧描述，把对应图片绘制到 Canvas 上，并且在每一帧结束时请求下一帧 | Canvas 接口与应用层 | 只能部分覆盖，绘制结果本身不做像素级断言 |
| 前端适配层 | `src/platform/` | 把应用层的请求翻译成对 Tauri 接口的调用，例如设置窗口位置、切换置顶状态、读写配置文件 | `@tauri-apps/api` 与应用层定义的接口 | 只能部分覆盖，可以通过替换 Tauri 接口的桩对象验证调用参数是否正确 |
| Rust 平台层 | `src-tauri/src/` | 创建窗口、设置置顶与鼠标穿透、注册系统托盘、读写配置文件、处理 Tauri 命令 | Tauri 框架与 Rust 标准库 | 纯计算部分用 cargo test 覆盖，涉及真实窗口的部分依靠手工验收清单 |

两条强制设计约束如下。

| 约束 | 具体要求 | 违反该约束产生的后果 |
|---|---|---|
| 时间由外部注入 | 领域层不调用当前系统时间，也不自行创建定时器；动画播放器的每次推进都接收一个毫秒增量参数 | 与动画帧推进有关的测试必须依赖真实等待，测试执行变慢，并且可能出现偶发失败 |
| 渲染由数据驱动 | 领域层不直接操作窗口或画布，而是输出一份帧描述对象，其中包含动画名称、帧索引、偏移量与可见性；渲染层负责把这份描述应用到画布上 | 领域层的断言只能依靠截图比对，测试脆弱，并且失败原因难以定位 |

## 5. 皮肤包规范

皮肤包是一个独立目录，目录名即皮肤标识，目录内必须包含一份 `skin.json` 清单与若干图片资源。

### 5.1 目录结构

```
assets/skins/<皮肤标识>/
  skin.json
  images/
    <帧图片文件>
```

### 5.2 清单字段

| 字段 | 是否必须 | 含义与作用 | 取值约束 |
|---|---|---|---|
| `id` | 必须 | 皮肤的唯一标识，用于配置文件记录当前使用的皮肤 | 必须与目录名完全一致，只允许使用小写字母、数字与连字符 |
| `displayName` | 必须 | 在右键菜单的皮肤选择项中显示的名称 | 长度在一到三十个字符之间 |
| `formatVersion` | 必须 | 皮肤格式版本号，加载器在版本不匹配时拒绝加载该皮肤 | 第一版取整数一 |
| `canvas.width` | 必须 | 逻辑画布宽度，单位为逻辑像素，用于确定窗口宽度 | 大于零的整数 |
| `canvas.height` | 必须 | 逻辑画布高度，单位为逻辑像素，用于确定窗口高度 | 大于零的整数 |
| `anchor.x` | 必须 | 锚点在画布中的横坐标，通常取宠物脚底中心 | 取值范围在零到画布宽度之间 |
| `anchor.y` | 必须 | 锚点在画布中的纵坐标，通常取宠物脚底中心 | 取值范围在零到画布高度之间 |
| `animations` | 必须 | 动画集合，键名为动画名称 | 至少包含 `idle` 与 `drag` 两个键 |
| `animations.idle` | 必须 | 待机动画，宠物静止时循环播放 | 加载器在缺少该动画时拒绝加载该皮肤 |
| `animations.drag` | 必须 | 拖拽动画，用户按住宠物并移动时循环播放 | 加载器在缺少该动画时拒绝加载该皮肤 |
| `animations.<名称>.fps` | 必须 | 该动画的播放帧率 | 必须大于零并且不超过六十 |
| `animations.<名称>.loop` | 必须 | 该动画是否循环播放 | 布尔值 |
| `animations.<名称>.frames` | 必须 | 帧描述数组 | 数组不能为空 |
| `animations.<名称>.frames[].file` | 必须 | 帧图片相对于皮肤目录的路径，加载器校验该文件是否存在 | 路径不得包含上两级目录符号 |
| `animations.<名称>.frames[].durationMs` | 可选 | 该帧的独立持续时间 | 当该字段存在时优先于由 `fps` 推算出的时长；取值必须大于零 |
| `hitbox` | 可选 | 可交互区域，用于鼠标命中判定 | 当该字段不存在时默认取整个画布 |

### 5.3 加载阶段的校验规则

加载器必须在加载阶段完成全部校验，并且把失败原因以可读文本返回，不能在播放过程中才暴露问题。

| 编号 | 校验规则 | 失败时返回的原因文本 |
|---|---|---|
| S1 | 清单文件存在并且可以被解析为对象 | 皮肤清单文件不存在或格式非法 |
| S2 | `formatVersion` 与加载器支持的版本一致 | 皮肤格式版本不受支持 |
| S3 | `id` 与皮肤目录名一致 | 皮肤标识与目录名不一致 |
| S4 | 存在 `animations.idle` 与 `animations.drag` 两个动画 | 皮肤缺少必要的待机动画或拖拽动画 |
| S5 | 每个动画的 `fps` 在合法区间内 | 动画帧率必须大于零并且不超过六十 |
| S6 | 每个动画的帧数组非空 | 动画的帧序列为空 |
| S7 | 每个帧文件在磁盘上真实存在 | 帧文件缺失，并附上具体路径 |
| S8 | 锚点坐标落在画布范围之内 | 锚点坐标超出画布范围 |
| S9 | 画布宽高为正整数，命中区域在存在时宽高为正数，帧的独立持续时长在存在时为正数 | 画布尺寸必须都是大于零的整数 |

## 6. 行为契约

### 6.1 状态机

第一迭代只有两个状态，状态之间的迁移由四类事件触发。

| 当前状态 | 事件 | 下一状态 | 附带动作 |
|---|---|---|---|
| 待机 | 鼠标在宠物可交互区域内按下 | 拖拽中 | 记录按下位置与宠物当前位置的差值，把当前动画切换为 `drag`，把帧索引重置为零 |
| 拖拽中 | 鼠标移动 | 拖拽中 | 桌面端由操作系统接管拖动，程序只回读窗口左上角并换算成锚点后提交渲染，不回写窗口位置；没有系统级拖动的环境按「窗口当前位置等于指针当前位置减去按下时记录的差值」计算新位置，再经位置约束器夹紧后提交渲染 |
| 拖拽中 | 鼠标松开或窗口位置连续静止四百毫秒 | 待机 | 把当前动画切换为 `idle`，把帧索引重置为零，把最终位置写入配置文件 |
| 待机 | 右键菜单中的置顶开关命令 | 待机 | 翻转置顶状态，把新状态写入配置文件 |
| 两种状态均可 | 右键菜单中的退出命令 | 程序终止 | 把当前位置与置顶状态写入配置文件后退出进程 |

### 6.2 事件类型

| 事件 | 携带的数据 | 产生来源 |
|---|---|---|
| 鼠标按下 | 指针的屏幕坐标 | 渲染层的指针按下监听 |
| 鼠标移动 | 指针的屏幕坐标 | 渲染层的指针移动监听 |
| 鼠标松开 | 指针的屏幕坐标 | 渲染层的指针松开监听 |
| 菜单命令 | 命令标识，取值为置顶开关或退出 | 右键菜单的点击回调 |
| 动画推进 | 自上次推进以来经过的毫秒数 | 适配层的渲染循环 |

### 6.3 位置约束

位置约束器接收一个候选坐标与一组显示器工作区，返回一个被夹紧到合法范围的坐标。夹紧规则是：先找出包含候选坐标的那一块显示器工作区，当候选坐标不落在任何一块工作区内时取距离最近的显示器工作区；再以该显示器工作区为边界，把宠物的锚点坐标限制在工作区内部，从而使宠物不会被拖到屏幕可视范围之外而无法再次找回。

## 7. 配置持久化

配置文件保存在用户数据目录下，文件名固定为 `config.json`。

| 字段 | 类型 | 含义 | 缺省值 |
|---|---|---|---|
| `activeSkinId` | 字符串 | 当前使用的皮肤标识 | `default` |
| `alwaysOnTop` | 布尔值 | 窗口是否置顶 | `true` |
| `anchorPosition.x` | 数字 | 宠物锚点在虚拟屏幕坐标系中的横坐标 | 主显示器工作区中心点的横坐标 |
| `anchorPosition.y` | 数字 | 宠物锚点在虚拟屏幕坐标系中的纵坐标 | 主显示器工作区底边的纵坐标 |

当配置文件不存在、无法解析或者字段缺失时，程序必须使用缺省值继续启动，并且把补齐后的完整配置写回文件，不能因为配置损坏而拒绝启动。

### 9.3 手工验收清单

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| M1 | 透明背景 | 在三个平台上运行时，宠物周围的区域完全透出桌面内容，不出现黑底或灰底 |
| M2 | 置顶效果 | 打开浏览器并最大化后，宠物仍然显示在浏览器窗口之上 |
| M3 | 拖拽平滑度 | 按住宠物移动鼠标时，宠物跟随指针移动，不出现明显滞后或残影 |
| M4 | 右键菜单 | 在宠物可见区域内点击鼠标右键，菜单在三个平台上都能弹出，并且包含置顶开关与退出两项 |
| M5 | 托盘图标 | 程序启动后托盘区域出现图标，并且菜单中的显示窗口与退出两项都能正常工作 |
| M6 | 位置记忆 | 把宠物拖动到屏幕右下方，退出程序后重新启动，宠物出现在上次的位置 |
| M7 | 皮肤切换 | 在右键菜单中选择另一份皮肤后，宠物立即更换外观，并且动画继续播放 |
